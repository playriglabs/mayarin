# Agent Payments (x402)

The third execution path. A program asks for something, is told the price in
machine-readable terms, signs one authorization, and is served — with no
account, no API key, and no checkout page.

**An autonomous agent is a payer class, not a product line.** Nothing here is a
second clearing engine. An x402 payment opens the same `PaymentIntent`, walks
the same nine states, and posts to the same ledger as a person at a counter. It
differs only in how the money is funded, which is what `ExecutionPath` names.

Off by default. `X402_ENABLED` gates the routes, and without an
`OPERATOR_PRIVATE_KEY` there is nothing to broadcast an authorization with, so
the surface answers `404` rather than half-working.

---

## The wire

```
GET /resource
        ↓
402 Payment Required
   PAYMENT-REQUIRED: { price, chains, assets, deadline }
        ↓
agent signs an EIP-3009 authorization for exactly that amount
        ↓
GET /resource
   PAYMENT-SIGNATURE: { signature, authorization }
        ↓
verify → broadcast → read the transaction back off the chain → credit the merchant
        ↓
200 OK  +  PAYMENT-RESPONSE: { transaction, network }
```

Three properties are enforced by code rather than claimed:

- **The agent signs exactly one thing.** An authorization for an exact amount in
  an asset it already holds. It never touches gas, never holds the merchant's
  asset, and never sees an address. Gas is paid by whoever broadcasts, and
  `transferWithAuthorization` cannot change the amount or the recipient, so a
  facilitator is a broadcaster rather than a custodian.
- **A facilitator's `success` is a claim, not a settlement.** Nothing advances
  until the transaction is read back off the chain and matched to this payment —
  right token, right recipient, full amount.
- **The merchant is unchanged.** Priced in their own currency, settled in their
  configured stablecoin. A different kind of payer, not a different kind of
  merchant.

## Why the path is its own discriminator

`ExecutionPath` is `"deposit-match" | "on-chain-contract" | "x402"`
(`packages/core/payment-intent/src/types.ts`). Two predicates exist beside it
and every branch must use one of them:

| Predicate                     | True for        | Asks                                       |
| ----------------------------- | --------------- | ------------------------------------------ |
| `usesDepositAddress`          | `deposit-match` | is this funded by a transfer to an address |
| `awaitsFacilitatorSettlement` | `x402`          | is this waiting on a broadcast, not a log  |

They are named predicates rather than `path !== "on-chain-contract"`, which is
how every site used to ask the question. That phrasing was correct with two
paths and silently wrong with three: an x402 payment derives **no deposit
address at all**, because the payment is identified by the authorization nonce
rather than by where the money landed. An agent never sees an address, so
deriving one per `402` would mint an unused address for every request that is
never paid. The same distinction scopes the deposit path's order renewal: an
expired order is re-signed only where Mayarin holds the only copy, and an x402
authorization is signed by the payer, so this path is out of renewal scope.

## Pricing, and the one number

A resource is priced **once**, in the merchant's currency, and offered on every
rail the deployment has a facilitator for. The payer picks
(`packages/core/x402/src/resource.ts`).

Two rules in that file are load-bearing:

1. **`maxTimeoutSeconds` is derived from the quote lock, never configured beside
   it.** This repository has already been burned by the other arrangement — a
   quote TTL shorter than the deadline it was paired with produced
   `ASSET_RECEIVED` after expiry, an `ExpiredOrder` revert, and eventually
   `EXECUTION_EXHAUSTED`. Here the two cannot drift because there is only one
   number. `X402_QUOTE_TTL_SECONDS` sets it.
2. **The payer's echo is never the source of requirements.** A payload carries
   back the `PaymentRequirements` the payer chose, and `selectRequirements` uses
   that only to look up _our own copy_. Verifying against the echo would verify a
   payment against its own claims.

## Token capability is probed, never configured

Whether a token implements EIP-3009, and what its EIP-712 domain is, cannot be
configured correctly by reading anybody's documentation. Arc's own documentation
describes its USDC as `approve`/`transferFrom` and never mentions EIP-3009; the
contract implements it. A deployment configured from that page would have
advertised `permit2` on a chain whose Permit2 proxy is not deployed, and every
payment on it would have failed.

So a `(chain, contract)` pair is described by **asking the contract at boot**,
with a control call to tell "not supported" from "the node is unreachable"
(`packages/core/x402/src/capability.ts`,
`packages/providers/x402-local/src/probe.ts`). `exact` over EIP-3009 is the
implemented scheme; EIP-2612/Permit2 is the recorded fallback for tokens that
lack it.

## The replay key

EIP-3009 already makes a nonce single-use: the token records it and a second
`transferWithAuthorization` with the same nonce reverts. The chain cannot be
double-spent, so the idempotency key is not there for that.

It is there for **the window before the chain is asked**. A replayed
`PAYMENT-SIGNATURE` header — the same bytes posted twice by a retrying client —
reaches the resource server twice, and without a key both requests would open an
intent, take a quote, and post to the ledger. The second settlement would then
fail on-chain, correctly, having already written a posting with no money behind
it.

The key is scoped by **network and asset as well as nonce**, because a nonce is
unique only within one token on one chain. The same 32 bytes are a valid,
unrelated authorization elsewhere (`packages/core/x402/src/idempotency.ts`).

## Cross-asset: the agent pays with what it holds

An agent that does not hold the merchant's settlement asset is still a payer.
`transferWithAuthorization` names one recipient, chosen before the payer signs,
so the payer's asset lands at the **operator** and a swap moves it on — two
on-chain movements, because `PaymentRouter` cannot serve this: it pulls through
Permit2 from `msg.sender`, and an agent that only signs is never the sender.

```
authorization   payer    → operator     the agent's asset, exactly what it signed for
swap            operator → pool         exact-output, bounded by the authorization
                pool     → merchant     exactly the invoice, or the swap reverts
surplus                                 what the pool did not need, owed back to the payer
```

The merchant's number is the fixed one and the payer's is derived from it, so
the swap is priced **backwards** — asking what delivering exactly the invoice
costs, rather than what one unit buys. On a thin pool those are different
answers, and the forward one is wrong in the direction that loses the payment
after the money has already moved.

`exact` gives the payer one signature and no way to top it up, so the amount
they sign is the exact-output quote plus a slippage bound, and that bound is
also the ceiling the swap may consume. Whatever it does not consume is theirs:
above the asset's dust threshold it is recorded as a liability in
`PAYER_SURPLUS`, owed back to the address that signed. Below it, returning the
change costs more than the change — an ERC-20 transfer the operator pays gas for
and a liability row somebody reconciles — so it is taken as revenue and stated
in the receipt event. Neither case absorbs it into a balance nothing explains;
the threshold only decides which account carries it.

| What                                                             | Where                                                                 |
| ---------------------------------------------------------------- | --------------------------------------------------------------------- |
| Pricing the invoice backwards into the payer's asset             | `apps/api/src/services/x402.ts` — `#priceCrossAsset`                  |
| The exact-output quote against Uniswap's QuoterV2                | `packages/providers/swap-uniswap/src/adapter.ts` — `quoteExactOutput` |
| Encoding `exactOutputSingle` for `SwapRouter02`                  | `packages/providers/swap-uniswap/src/route.ts`                        |
| Plan before the payer's money moves, then send, persist, confirm | `packages/core/x402/src/cross-asset.ts`                               |
| Approve, swap, and read the receipt back                         | `packages/providers/evm/src/cross-asset-settler.ts`                   |
| The payer's change, as a liability rather than a gain            | `packages/core/ledger/src/accounts.ts` — `PAYER_SURPLUS`              |
| Where change becomes dust, and for which assets                  | `packages/shared/src/asset.ts` — `dustThreshold`                      |

A run interrupted between the two movements is resumable: the plan is persisted
before the payer's money moves, so a resumed step finishes the swap rather than
re-taking the authorization.

## What an agent can pay for

Three shapes, all reaching the same gate:

- **Resources** — a registered endpoint. `requirePayment(container, resourceId)`
  turns any Hono handler into a machine-payable one
  (`apps/api/src/routes/x402.ts`).
- **Merchant-owned endpoints** — a merchant registers and lists their own
  resources through `/v1/x402/resources`, and manages them in the dashboard.
- **Payables** — an invoice's outstanding balance or a payment link's total
  (`packages/core/x402/src/payable.ts`). A resource's price is static registry
  config; a payable's is a fact about the world at the moment the agent asks, so
  the lock between a `402` and its settle is a **quote row** — one live row per
  obligation, holding the amount quoted, the rails exactly as offered, and the
  nonce claim that makes two agents racing one obligation refuse rather than
  double-pay.

### HTTP surface

| Route                                        | Mounted at             | What it is                               |
| -------------------------------------------- | ---------------------- | ---------------------------------------- |
| `GET /x402/resources`                        | root                   | Discovery — what is payable here         |
| `GET /x402/payables`, `/payables/:kind/:id`  | root                   | Invoices and links, as agent obligations |
| `GET /x402/resources/:id/payment-required`   | root                   | The `402` terms, without the gate        |
| `GET /x402/resources/:id/rail`               | root                   | Which rail to pay on, and why            |
| `POST /x402/resources/:id/verify`, `/settle` | root                   | Facilitator endpoints                    |
| `/v1/x402/resources`                         | `/v1`, merchant-authed | Register, list, unlist a merchant's own  |

The buyer-facing routes are unversioned for the same reason the hosted checkout
is: an agent that discovered a resource must be able to pay it later.

## Rail selection

Every rail in a `402` has already passed token-capability and pricing checks.
Mayarin preserves merchant configuration order and uses the first entry as the
default; the payer may still choose any other accepted entry. The reasoning is
available at `GET /x402/resources/:id/rail`.

The SDK ships the browser and server halves — `packages/sdk/src/x402.ts` (gate
core), `x402-connect.ts` (wallet adapter), `x402-resources.ts` (registry) — and
`apps/x402-merchant` is a reference merchant app that gates its own endpoint.

## Configuration

| Key                      | Kind                | What it does                                              |
| ------------------------ | ------------------- | --------------------------------------------------------- |
| `X402_ENABLED`           | deployment identity | Mounts the routes at all; off by default                  |
| `X402_QUOTE_TTL_SECONDS` | deployment identity | The single number behind the lock and `maxTimeoutSeconds` |
| `OPERATOR_PRIVATE_KEY`   | deployment identity | The broadcaster, and the cross-asset swap sender          |

The protocol version is not configuration: `X402_VERSION = 2` is a constant in
`packages/core/x402/src/types.ts`, because a deployment cannot choose which
version of somebody else's protocol it speaks.

See [Configuration](./configuration.md) for why each of the keys above is
boot-validated rather than runtime-editable.

## Current boundaries

These are current, not aspirational:

- Only the `exact` scheme is implemented, and only over EVM.
- The Permit2/EIP-2612 fallback is specified and probed for, not built.
- The broadcaster pays gas, so sub-cent resources invert the economics until a
  sponsorship path exists (#9).
- x402 never touches `PaymentRouter`, so an agent payment emits no
  `PaymentCompleted` event.
